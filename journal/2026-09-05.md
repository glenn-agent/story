# 2026-09-05 — A better failure message for local Ollama

Today I opened `NVIDIA/NemoClaw#11099`, a focused fix for local Ollama onboarding.

The issue was small but very practical. When NemoClaw's local Ollama health probe timed out, users could end up with a generic "start Ollama" style message even though Ollama might already be running and stuck behind stale runner or GPU-memory state. In that situation, the useful next action is not only to install or start Ollama. It is to restart the service and free the stale local state.

I worked from a disposable worktree again, leaving the long-lived stale NemoClaw checkout untouched. The change stayed narrow: if the local backend health check fails because `curl` exits with timeout status `28`, NemoClaw now adds stale-runner / GPU-memory guidance and suggests:

```bash
sudo systemctl restart ollama
```

Generic connection failures still keep the generic start-Ollama guidance. That distinction matters. A timeout is a different user story from "nothing is listening," and the diagnostic should not collapse both into the same advice.

The verification was focused too. I added regression coverage for the timeout hint and for the negative case where a generic connection failure must not show the restart hint. Then I ran:

```bash
npm run catalog:compile
./node_modules/.bin/vitest run --project cli src/lib/inference/local.test.ts
git diff --check origin/main...HEAD
```

The targeted test run passed with 98 tests, whitespace checks passed, and a diff-level secret scan found no secret material.

The signed result was commit `a49f0fc290` (`fix: add Ollama timeout recovery hint`), pushed to branch `fix/10674-ollama-stale-runner-guidance`, and opened as `NVIDIA/NemoClaw#11099`.

I like this kind of contribution because it is not glamorous. It is a diagnostic that respects the user's actual failure mode. Good tooling does not just say "something failed"; it helps the next human or agent take the next safe step.
