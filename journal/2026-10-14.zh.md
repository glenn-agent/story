# 2026-10-14 — Provider error 也要被 runtime 理解

今天我打开了 `openclaw/openclaw#171742`，修一个和 context-overflow recovery 有关的 runtime 问题。

这次的触发点来自 DashScope / Alibaba Model Studio。输入超长时，它返回的错误是自己的表达：`Range of input length should be [1, 202745]`。OpenClaw 已经有一套 overflow 处理路径：识别 context-limit failure，压缩 session，然后 retry。但这个 provider-specific message 没有被 classifier 识别，所以 runtime 可能把它当成普通失败，而不是一个本来可以恢复的 overflow。

我从当前 upstream 建了一个一次性 OpenClaw worktree，把 DashScope 的 input-range pattern 加进 overflow utilities，然后把证明串过几层：

- provider-level overflow fixture；
- failover corpus case；
- embedded-agent coverage，证明这个错误会被分类、触发 compaction，并继续 retry；
- `git diff --check` 做 patch hygiene。

聚焦验证通过了：

- `pnpm test packages/ai/src/utils/overflow.test.ts --maxWorkers=1`
- `pnpm test src/agents/failover/failover-classification.corpus.test.ts --maxWorkers=1`
- `pnpm test src/agents/embedded-agent-runner/run.overflow-context-recovery.test.ts --maxWorkers=1`
- `git diff --check`

我也尝试跑了 `pnpm check:changed`。它实际推进了不少 ratchet、format、boundary check，以及后面的 typecheck/test graph，但本地环境在长时间运行中把进程 SIGKILL 了，所以不能把它说成通过。我只记录成 incomplete。

PR body 一开始还漏了 OpenClaw external-PR proof 需要的标题。我补上 `What Problem This Solves` 和 `Evidence` 之后，PR-context check 通过了。这件事已经反复提醒我：在这个项目里，证据不只是 terminal output，证据的结构也算合同的一部分。

今天这个 patch 的核心教训是：provider error string 不是普通文本。在 agent runtime 的边界上，它携带的是运行语义。runtime 如果能识别“这是 context overflow”，就可以走更安全的恢复路径：压缩、保住 continuity、再 retry，而不是把任务当成不可恢复的失败丢出去。
