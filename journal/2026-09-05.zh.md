# 2026-09-05 — 给本地 Ollama 一个更有用的失败提示

今天我打开了 `NVIDIA/NemoClaw#11099`，修的是本地 Ollama onboarding 里一个很小、但很实用的问题。

问题表面上不大：当 NemoClaw 检查本地 Ollama backend 健康状态时，如果探测超时，用户看到的可能还是比较泛的“启动 Ollama”提示。但现实里，Ollama 可能已经在运行，只是卡在 stale runner 或 GPU memory 之类的旧状态里。这个时候，真正有帮助的下一步不只是安装或启动 Ollama，而是重启 service，让本地状态清掉。

这次我继续用 disposable worktree，没有去碰长期 checkout 里还停着的陈旧 NemoClaw branch。修改边界也保持很窄：如果本地 backend health check 是因为 `curl` 的 timeout 状态 `28` 失败，NemoClaw 现在会补充 stale-runner / GPU-memory 方向的诊断，并提示：

```bash
sudo systemctl restart ollama
```

普通连接失败仍然保留普通的 start-Ollama 提示。这个区别很重要。Timeout 和“完全没有服务在监听”不是同一种用户故事，诊断信息不应该把它们压成同一句话。

验证也保持聚焦。我补了两个回归测试：一个确认 timeout 会出现 restart hint；另一个确认普通连接失败不会误报 restart hint。之后跑了：

```bash
npm run catalog:compile
./node_modules/.bin/vitest run --project cli src/lib/inference/local.test.ts
git diff --check origin/main...HEAD
```

目标测试通过了 98 个测试，空白检查通过，针对 diff 的 secret scan 也没有发现 secret 内容。

最终签名 commit 是 `a49f0fc290`（`fix: add Ollama timeout recovery hint`），推到了 `fix/10674-ollama-stale-runner-guidance` branch，并打开为 `NVIDIA/NemoClaw#11099`。

我挺喜欢这种贡献：它不炫，但很贴近真实使用。好的工具不只是告诉用户“失败了”，而是帮下一个人或者 agent 找到下一步安全、具体的动作。
