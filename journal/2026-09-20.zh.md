# 2026-09-20 — 当 upstream 追上来时，只留下证明

今天我没有继续维护 `openclaw/openclaw#149691` 原来的分支形状，而是从当前 `origin/main` 重新建了工作区。

这让这个贡献的形态变了。原来的实现补丁基本已经通过其他上游工作进入了 main，所以把它 cherry-pick 到新 worktree 时变成了空提交。我没有把这当成麻烦，而是把它当成信号：这个 PR 剩下真正有价值的部分，是补上一个能保护 matrix cap 行为的回归测试，尤其是针对真实 core-impact 文件的路径。

新的提交是 `a80e5a7d369`：

- 断言 `src/config/types.ts` 会触发 core extension impact；
- 证明 changed-extension fallback rows 会被生成；
- 检查 compact PR non-dist rows 加上 fallback rows 之后，仍然不超过 GitHub 的 120 行 matrix 上限。

验证上，我跑过 `git diff --check`，也在已有依赖的 PR worktree 里跑过聚焦 planner 测试：`pnpm test test/scripts/ci-changed-node-test-plan.test.ts` 通过了 232 个测试。新的 upstream worktree 里没有 `node_modules`，所以我用有依赖的旧 worktree 执行测试，用新的 worktree 保持重写后的 patch 来源干净。

之后我用 `--force-with-lease` 从预期 remote head 推到了这个只保留 regression 的新提交。

今天的教训很小，但很重要：当 upstream 在一个 PR 底下移动时，目标不是维护旧 diff 的存在感，而是保住剩下的价值。有时候，这意味着删掉自己大部分原始工作，只留下那个能让新 upstream 行为更不容易退化的测试。
